# NovelMind 从零到完整项目的代码阅读指南

这份指南写给会 Python 基础语法、但还没有完整项目经验的读者。目标不是让你
背诵每个函数，而是让你理解：一个真实项目如何从问题出发，逐步变成可运行、
可测试、可升级、出错后可恢复的软件。

代码中的注释负责解释“这一段为什么这样写”；本文负责解释“整个项目为什么
按这个顺序长出来”。第一次阅读时不要从最大的文件逐行硬啃，请按下文路线走。

如果看到类型注解、装饰器、依赖注入、`yield`、ORM、异步或 Protocol 等陌生
语法，请随时对照 [项目 Python 语法指南](python_syntax_guide.md)。

## 一、先建立项目全景

NovelMind 是 Windows 本机单用户应用，但仍采用前后端分离：

```text
用户
  ↓ 浏览器
原生 HTML/CSS/JavaScript 网页
  ↓ HTTP/JSON
FastAPI 后端
  ├─ SQLite 主数据库
  ├─ 本地 SQLite + NumPy 向量库
  └─ 外部生成 / embedding API
```

每层只承担自己的职责：

- 前端负责展示、交互和短期页面状态，不直接读写数据库；
- API 负责请求校验、授权、事务边界和稳定的 HTTP 响应；
- analyzer / rag 负责耗时业务编排；
- models 描述长期数据和数据库一致性约束；
- 外部模型负责语义生成，本地代码负责证据、权限、上限和结果校验。

“本机单用户”不等于可以省略工程边界。浏览器会并发请求，后台任务会同时写库，
外部 API 会超时或限流，进程也可能在任务中途退出。这里的多数可靠性设计正是
为这些现实情况服务。

## 二、推荐阅读顺序

### 第 1 站：看项目怎样启动

先读：

1. `backend/app/main.py`
2. `backend/app/core/database.py`
3. `scripts/novelmind_launcher.py` 的模块说明、`start()` 和 `stop()`

你应能回答：

- `uvicorn backend.app.main:app` 怎样找到 FastAPI 对象？
- 为什么数据库初始化必须发生在接收请求前？
- 为什么单个应用仍要分别检查 API 健康和网页就绪？
- 为什么进程存在不等于服务已经就绪？
- 异常退出时谁负责结束子进程、修正遗留任务？

### 第 2 站：走通最小数据闭环

依次读：

1. `backend/app/parser/chapter_splitter.py`
2. `backend/app/models/novel.py`
3. `backend/app/api/novels.py`
4. `frontend/web/api.js` 的上传和资料库函数
5. `frontend/web/pages.js` 的上传、资料库和阅读器部分

跟踪一份 TXT：原始字节怎样经过大小/扩展名/编码/乱码检查，怎样切成章节，
怎样在一个事务中写入小说与章节，再怎样经 JSON 返回并显示。这个闭环包含了
典型项目最基本的输入、业务规则、持久化、API 和 UI。

### 第 3 站：理解配置不是几个全局变量

读 `backend/app/core/config.py` 和 `backend/app/api/system.py`。

注意这些问题：

- 字符串环境变量怎样变成正整数、枚举和可选值？
- 为什么外部 HTTP 端点必须限制协议、凭据、查询参数和域名？
- 为什么 Settings 不可变？
- 为什么运行中的任务继续使用旧配置快照？
- 为什么状态接口只能返回 `api_key_configured: true/false`？
- 为什么配置文件要先写临时文件再原子替换？

配置是系统边界。越靠近底层的错误越应该尽早失败，否则它会在很远的模型调用
中以难以理解的形式出现。

### 第 4 站：理解后台任务状态机

读：

1. `backend/app/models/analysis.py`
2. `backend/app/api/summaries.py` 的启动与查询接口
3. `backend/app/analyzer/jobs.py`
4. `backend/app/analyzer/summaries.py` 的 job runner

状态通常按以下方向移动：

```text
queued → running → succeeded
                 ↘ failed
```

接口不等待几十次外部调用，而是先提交 queued 记录并立即返回任务 ID。前端轮询
任务状态。执行器用条件更新 claim 任务，避免同一任务被重复派发后执行两次。
成功、失败、进度都持久化，所以刷新页面不会丢失状态。

重点理解两个故障窗口：

1. 事务尚未提交，后台线程就开始查询：它会找不到任务；
2. 事务已经提交，但后台派发失败：会留下永远 queued 的任务。

因此代码采用“先提交、后派发、派发失败则补偿终结”。这类思维比记住某个
FastAPI API 更重要，它适用于邮件发送、导出、支付回调等许多后台工作。

### 第 5 站：理解外部模型不是普通函数

读：

1. `backend/app/analyzer/llm.py`
2. `backend/app/analyzer/deepseek.py`
3. `backend/app/analyzer/prompting.py`
4. `backend/app/analyzer/summaries.py`

外部模型调用具有网络失败、认证失败、余额不足、限流、返回非 JSON、JSON 字段
错误、结果过长等多类风险。代码把它们拆开，是因为处理方法不同：认证失败不应
盲目重试，限流可以退避，结构错误可向模型提供不含敏感数据的有限纠错反馈。

模型输出必须经过两层验证：

- JSON 语法是否可解析；
- Pydantic 业务结构是否满足字段、长度、类型和交叉规则。

提示词只是要求，不是安全边界。真正边界必须由本地确定性校验执行。

### 第 6 站：理解缓存与来源哈希

摘要、人物、RAG、报告都包含 source hash。它回答的不是“数据库有没有记录”，
而是“这条记录是否由当前输入、当前提示规则和当前模型配置生成”。

典型思路：

```text
hash(原始内容 + 影响结果的版本信息) == 已保存 source_hash
    → 可以复用
否则
    → 结果过期，需要重建
```

这叫内容寻址或派生数据失效。加入一个会影响结果的新参数时，必须把它纳入哈希
或提升版本；否则系统会错误复用旧结果。不要用更新时间猜测内容是否相同。

### 第 7 站：理解原子快照

人物、RAG 和报告都采用“成功后整体替换当前快照”，而不是边生成边让用户看见。

人物流水线：

```text
逐章缓存 → 全书归并 → 身份调和 → 关系推理 → 单事务替换人物快照
```

RAG 索引：

```text
确定性分块 → 复用旧向量 → 生成缺失向量 → 写新集合
→ 校验数量 → 单事务切换主库指针 → 清理旧集合
```

报告：

```text
复核摘要/人物来源 → 分批证据笔记 → 分层归并 → 最终报告
→ 校验全部引用 → 单事务替换报告快照
```

共同原则是：旧版本在新版本完整通过之前一直可用。失败不会把用户从“有一份
旧结果”降级成“只有半份新结果”。数据库事务和版本化集合分别提供不同介质上
的原子性。

### 第 8 站：完整理解 RAG

依次读：

1. `backend/app/rag/chunking.py`
2. `backend/app/rag/embedding.py`
3. `backend/app/rag/vector_store.py`
4. `backend/app/rag/indexer.py`
5. `backend/app/rag/answering.py`
6. `backend/app/api/rag.py`

RAG 不是“把全文发给模型”。本项目的流程是：

1. 按稳定规则切分章节；
2. 把分块发给 embedding 服务获得向量；
3. 在本地保存向量，不复制原文；
4. 问题也生成向量；
5. 本地余弦检索相似分块；
6. 用命中位置回查主数据库原文；
7. 校验章节归属、范围和正文哈希；
8. 只把少量验证后的证据发给生成模型；
9. 检查模型引用是否来自本次白名单。

向量相似只说明“可能相关”，不说明内容真实，也不能取代主数据库。证据复核与
引用白名单让回答可追踪，而不是把模型流畅表达误当成正确性。

### 第 9 站：读前端时记住 rerun 模型

历史兼容界面 Streamlit 的按钮点击、选择变化会让脚本重新从上到下运行（代码位于 legacy/streamlit/）。普通局部变量会消失，
`st.session_state` 才能保存当前页面、小说 ID 和分页位置。长期业务状态不应塞入
session_state，而应从后端重新读取，这样刷新浏览器和重启前端仍能恢复。

前端代码可分三类：

- `_require_*`：验证 API 响应结构；
- 小型 `render_*`：可复用展示组件；
- 页面级 `render_*_workspace`：组合数据加载、按钮和局部状态。

不要在渲染函数里复制后端业务判断。界面可以提前给友好提示，但数据库一致性、
授权和并发冲突仍必须由后端重新验证。

## 三、一个项目从零到当前形态的合理实现顺序

### 1. 写清问题与边界

先回答：为谁解决什么问题？哪些数据留在本地？哪些必须发到外部？MVP 不做什么？
本项目的答案记录在 `docs/product_requirements.md`。没有边界就会同时开工 UI、
模型、数据库，最后每层都不断返工。

### 2. 建目录和最小可运行入口

先让 `/health` 能返回，网页能显示，测试能导入模块。最小入口验证 Python
版本、依赖、包路径和启动命令；此时不要急着实现最复杂的 RAG。

### 3. 完成一个不依赖外部 API 的垂直切片

上传 TXT → 切章 → 保存 → 列表 → 阅读，是理想第一条闭环。它能验证数据模型、
事务、HTTP、前端通信和错误提示，同时测试便宜、确定、无需密钥。

### 4. 先定义外部服务契约，再接真实供应商

用 Protocol 定义业务真正需要的最小能力，再写 DeepSeek/embedding 实现。测试用
假实现返回固定数据。这样单元测试不会花钱，也不会因网络波动变红。

### 5. 为耗时功能设计持久任务

不要先写“循环调用模型”，再临时补进度。先定义状态机、任务表、重复任务规则、
失败终态和重启行为，然后实现执行器。任务系统是功能的一部分，不是 UI 装饰。

### 6. 为派生结果设计版本与失效

列出所有会改变结果的输入：正文、标题、模型、提示版本、分块版本、向量维度等。
决定哪些写入 source hash，哪些单独存列。没有失效规则的缓存迟早返回错误旧数据。

### 7. 为失败设计旧版本保留

生成新人物、索引和报告时，不要先删除旧数据。先在临时结构构造并校验，最终在
一个短事务里切换。用户数据与已付费生成结果应优先保住。

### 8. 增加迁移而不是修改历史假设

模型类描述“新安装应是什么样”，迁移描述“旧安装怎样安全到达这里”。发布后
新增列、索引、约束，应追加迁移并测试从旧结构升级。迁移前必须备份真实数据。

### 9. 测试正常路径、边界和故障路径

至少覆盖：

- 正常输入与最小/最大边界；
- 空值、错类型、乱码、重复请求；
- 数据库约束和事务回滚；
- 外部超时、限流、非 JSON、结构错误；
- SQLite 锁冲突和有界重试；
- 派发失败、重复派发、进程重启；
- 来源变化、旧缓存、缺失向量集合；
- 前端收到畸形响应时能否安全提示。

测试不是证明软件绝无错误，而是把已经确定的重要行为变成可重复检查的合同。

### 10. 最后完善启动、日志、备份和文档

“代码能跑”不等于用户能稳定使用。还需要固定启动命令、健康检查、日志位置、
安全停止、配置样例、备份说明、故障排查和版本记录。项目交付包括这些运维细节。

## 四、常见误区与本项目中的对应做法

- **把 try/except 当成可靠性**：异常被捕获但任务没写终态，用户仍会永久转圈。
  本项目对提交后派发、运行失败和 SQLite 锁分别做补偿。
- **只在前端校验**：请求可绕过浏览器直接发送。关键授权与约束必须后端执行。
- **只在 Python 校验唯一性**：“先查没有，再插入”在并发下会竞态。数据库唯一
  约束才是最后防线，Python 检查只用于更友好提示。
- **把模型输出当对象使用**：可解析 JSON 仍可能字段错、引用假、ID 越界。
  Pydantic、白名单和本地交叉验证缺一不可。
- **先删除旧结果再刷新**：新生成失败会让用户一无所有。应构建新快照后切换。
- **用是否存在判断缓存有效**：原文或规则已改变时，存在的结果也可能过期。
- **在长事务中调用网络**：等待外部 API 时占着 SQLite 写锁会放大并发失败。
  应先读取/准备，释放事务，网络调用后再用短事务保存并复核来源。
- **日志记录一切方便调试**：正文、密钥、完整提示和模型推理可能是敏感数据。
  日志应记录任务 ID、阶段、错误类别等最小诊断信息。
- **看到内部函数以下划线开头就随意删除**：下划线表示模块内部约定，不表示
  没有调用。先用搜索和测试确认调用链。
- **把测试数量当质量**：更重要的是覆盖了哪些风险，测试是否真的在当前解释器、
  当前工作区运行，而不是引用旧版本的 passed 数字。

## 五、如何安全地练习修改

建议从小改动开始，例如增加一个只读元数据字段：

1. 写清字段来源和用户价值；
2. 判断它是计算值还是必须持久化；
3. 若持久化，修改模型并追加迁移；
4. 修改 API 响应模型；
5. 修改 `frontend/web/api.js`（如端点变化）；
6. 在 UI 严格验证并展示；
7. 增加模型、API 和前端测试；
8. 运行相关测试，再运行完整回归；
9. 更新架构/使用说明/开发日志；
10. 检查 `git diff`，确认没有密钥、数据库和无关格式化。

每次只解决一个清晰问题，提交也保持聚焦。遇到失败先收集数据库、日志、任务
记录和代码路径证据，再决定是否重试；外部 API 调用可能产生费用，盲目重跑不是
中性的排障动作。

## 六、读完后的自我检查

如果你能不看本文回答下面问题，就已经建立了完整项目的基本思维：

1. 为什么前端不直接访问 SQLite？
2. 为什么一次请求一个 Session，网络调用又不应占着写事务？
3. 为什么先提交任务再派发，派发失败还要补偿？
4. Python 唯一性检查为什么不能代替数据库唯一索引？
5. 原文改变后，系统怎样知道摘要、人物、索引或报告已过期？
6. 为什么模型返回 JSON 后仍需要 Pydantic 和本地白名单？
7. 为什么 RAG 命中要回查主库，而不能直接相信向量集合？
8. 为什么人物、索引和报告都保留旧快照直到新结果完整成功？
9. 为什么 Streamlit 的长期状态应放后端，页面选择才放 session_state？
10. 为什么数据库模型变化还需要迁移？
11. 为什么异常退出后的任务不能继续显示 running？
12. 为什么配置、日志和错误信息都要按敏感边界设计？

最后再通读 `docs/architecture.md`，你会发现架构文档描述“当前系统是什么”，
本文描述“为什么会形成这些结构以及怎样继续演进”。两者结合，再回到代码逐函数
阅读，会比一开始从四千行前端文件硬读更高效。

## 当前实现阅读补充

先读 `frontend/web/app.js` 的路由与生命周期，再读 `pages.js` 的页面数据接入、`tasks.js` 的处理计划与轮询。
原生网页使用事件回调和异步 HTTP；持久任务、阅读偏好、锚点、书签保存在后端，DOM 只是当前显示。
旧 Streamlit 的 rerun/session_state 教学仍适用于兼容目录，不能直接当作新网页执行模型。

`api/summaries.py`、`api/reports.py`、`api/rag.py` 的路由委托 `services/` 同名模块。
观察 `services/workflows.py` 怎样冻结配置并按顺序调用同一服务，不必为流程模拟一次 HTTP 请求。
人物大文件现为稳定导出入口，按 `character_pipeline` 的 payloads → extraction → merge → persistence → worker 阅读。
迁移从 `core/migrations.py` 的账本开始，再看 migration_steps 的历史版本；v10 管网页状态，v11 移除旧归属触发器。

### 阅读跨模块集成验收

`tests/integration/` 集中保存端点密钥生命周期、任务链配置冻结、历史库升级和真实启动器测试。
先读 `run_isolated.py` 如何隔离数据库、向量目录和配置，再读 `test_launcher_lifecycle.py` 与 `launcher_probe.py` 如何观察实际进程。
默认 pytest 包含该组；旧界面测试单独在 `tests/legacy/`，完整运行 `python -m pytest tests -q` 时一并执行。
