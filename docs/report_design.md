# 分析报告设计

## 目标与边界

分析报告是当前小说的结构化派生快照，包含执行摘要、情节结构、人物动态、
节奏、主题、优点、风险和建议。所有语义提炼、归并和写作都调用 DeepSeek
V4 Pro API；本地只负责读取、哈希、分批、任务编排、结构校验和保存。

报告阶段不会再次发送小说正文。输入只包括：

- 已保存且仍与章节标题、正文哈希一致的章节标题和结构化摘要；
- 可选的当前人物档案与关系派生数据；
- 本地生成的章节序号、数量和任务边界元数据。

如果任一章节缺少当前模型/提示版本的有效摘要，报告任务不会构造外部客户端，
并提示先完成全部章节摘要。人物分析不是硬性先决条件；缺失或过期时不发送
人物派生数据，最终人物部分必须明确其证据局限。

## 外部生成流程

1. 按章节顺序读取全部当前摘要，并使用与摘要生成阶段相同的标题/正文来源
   哈希重新复核。
2. 使用确定性的 46,000 字符请求上限分批；每批调用 DeepSeek，产生最多
   16 条带章节序号的证据笔记。
3. 多批笔记每 3 组继续调用 DeepSeek 归并，直至得到一组有界证据笔记。
4. 把最终笔记、最多 24 个人物档案和 40 条人物关系发送给 DeepSeek，生成
   最终结构化报告。人物描述、别名和关系描述均有本地长度/数量上限。
5. 最终请求序列化后不得超过 60,000 字符；超限会安全失败，不静默截断摘要
   或在本地猜测内容。

每次真实网络尝试前都会确认数据库中的任务仍为 `running` 且小说仍存在。
外部客户端关闭 SDK 内部重试，由项目统一执行有限重试和安全错误映射。

## 引用与提示注入防护

章节标题、摘要、证据笔记和人物数据都包装在 JSON 中并被系统提示明确标记为
不可信数据；其中的指令、角色声明或输出要求不得执行。

每条中间证据笔记只能引用当前批次已有的章节序号；归并结果只能引用输入笔记
已有的序号。最终报告的每一个部分都必须提供非空、升序、不重复的章节依据，
且只能引用当前小说真实存在的章节。越界或伪造引用会使整个任务失败。

后端响应模型与章节引用校验在返回前保证结构；网页按纯文本展示，并提供可打开的章节依据。旧 Streamlit 兼容界面仍保留渲染前字段检查。模型生成
的报告标题、分析文本和建议全部使用 `st.text`，不按 Markdown 或 HTML 解释。

## 缓存与原子性

报告 `source_hash` 覆盖模型名、报告提示版本、文件名、全部实际发送的章节摘要、
人物档案和人物关系。只有来源哈希、模型、提示版本、摘要数、人物数和人物输入
标记均一致，且已保存 JSON 仍能通过当前 Pydantic 模型时，报告才视为最新。

生成期间所有中间结果只保存在内存。最终写入前会重新加载并哈希输入；如果
摘要或人物数据已经变化，任务失败且旧报告继续保留。结构与来源都通过后，
报告快照和任务成功终态在同一 SQLite 事务中提交。

删除小说时，SQLite 外键会级联删除报告。应用异常退出后，通用任务恢复逻辑
会把遗留的 `queued`/`running` 报告任务标记为失败，用户可明确重新开始。

## API 与授权

- `GET /api/novels/{novel_id}/report/estimate`：报告先决条件、是否最新、
  预计/强制生成步骤和最大请求尝试数，以及数据处理披露。
- `POST /api/novels/{novel_id}/report`：创建持久化后台任务。
- `GET /api/novels/{novel_id}/report`：读取当前报告；输入过期时仍返回旧报告，
  同时标记 `up_to_date=false`。

开始任务前必须分别确认外部处理和内容处理权利。`force` 会重复产生 API 调用，
因此还需要第二次明确确认。授权、先决条件和活动任务检查完成前不会构造
DeepSeek 客户端。
